## 1. 使用方法与状态

任务状态采用：未开始、进行中、待审查、待集成、已验收、阻塞。只有主代理核对最终集成状态和证据后可以改为已验收；不能把 agent 自报完成直接当验收。

每次领任务登记：任务号、源码基线、所有者、独占文件、接口版本、实际请求模型/推理参数、验证路径、当前状态。表中拟新增文件可按实际实现合并，但职责不能暗移到其他所有者文件。

任务中的验证编号引用指导方案第 13 节。首次开发需读根 AGENTS、适用 C++/Qt、命名、编码、PowerShell 和临时存储技能；不要在本任务板复制另一套项目执行规范。

## 2. 模型配置：沿用 Sol / max 主导的原有规则

按用户 2026-10-06 最新澄清，**旧规则保留，不改成所有子代理同一型号**。根 AGENTS 已是 `gpt-6.1-sol / max` 主导：Sol 负责主导、实施与独立审查，Luna 提供只读调研，Astra 仅按明确条件加入。以下是原规则在本任务的具体分工，不是新的全局模型配置。

| 角色 | 职责 | 模型/推理 | 写入权限 |
| --- | --- | --- | --- |
| 主代理/集成负责人 | 范围、契约冻结、所有权、共享配置、整合、最终验收 | 期望 gpt-6.1-sol / max；按客户端实际配置报告，不冒称切换成功 | 仅主代理保留的文件 |
| 实施 A | 本体 API、SceneViewModel、历史及对应测试 | gpt-6.1-sol / max | 明确分派的独占文件 |
| 实施 B | 按波次负责 Core、视口、通信或 TS；每次只领一个模块包 | gpt-6.1-sol / max | 与 A/主代理不重叠 |
| 只读调研 Q | 对真实未知点搜集源码、测试或官方资料证据，不替主代理决策 | gpt-6-luna / max | 只读，不运行会生成产物的构建 |
| 独立审查 R | 审查未由自己实现的改动、契约和回归风险 | gpt-6.1-sol / max | 只读，问题交回所有者修复 |
| 专家 E | 满足根 AGENTS 8.8 的高风险边界、关键设计矛盾或深层故障聚焦复核 | gpt-6-astra / high | 默认只读，实施仍交给 Sol |

默认同时最多两个子 agent，主代理不占这两个名额。不为凑并发拆分小任务；审查者需要槽位时先让无独立工作的实现者结束。子 agent 不再创建孙 agent。

下例是实施/独立审查代理的调度参数，**不是已安装配置**。只读调研改为 `gpt-6-luna/max`；达到专家触发条件后才使用 `gpt-6-astra/high`：

```json
{
  "task_name": "api_document_state",
  "model": "gpt-6.1-sol",
  "reasoning_effort": "max",
  "fork_turns": "none",
  "message": "执行已批准任务 M1-01；仅写分派文件；具体任务包见当前消息。"
}
```

使用当前客户端真正支持的 agent 启动参数，不以角色名称、提示词或文件名代替模型设置。指定 override 时不要使用不允许 override 的全量历史继承。启动后检查工具/客户端能返回的模型与推理字段；只有请求参数而无底层元数据时，记录“启动参数已指定，底层路由未独立验证”。若该角色所需配置不支持/不一致，暂停受影响分派并报告；只能采用用户明确接受的备用方案，不默默换型号或降低推理级别。

普通独立审查使用未参与实现的 Sol/max；涉及真实认证/授权边界、并发一致性等高风险施工，或 Sol 无法消除的关键设计取舍/深层故障，按根 AGENTS 8.8 启用 Astra/high 聚焦复核，不能每一步都叠加专家。权限、需求或环境问题交给主代理报告，不能用更强模型代替必要确认。本轮没有改用户模型列表、CLI 配置、AGENTS 或后台进程。

## 3. 文件所有权与集成点

| 文件/范围 | 默认所有者 | 规则 |
| --- | --- | --- |
| `api/schema/**`、跨语言契约样例、兼容矩阵 | 主代理 | 先冻结；下游发现缺口通过变更请求，不自行修改 |
| 根/各模块 CMake、Presets、vcpkg、package manifest/lockfile | 主代理 | 首次建依赖与目标串行；可明确转交 TS 所有者后再锁定 |
| `src/editor/SceneViewModel.*`、历史/现有命令、`src/editor/api/**` | A | 一个所有者统一处理；M1/M2/M5/M6 不并行碰这些文件 |
| `src/core/Scene.*`、必要建模准备原语 | B（Core 波次） | 先冻结给 A 的接口；不顺手重构所有建模算法 |
| `src/renderer_gl/ViewportWidget.*`、`ViewNavigationWidget.*`、`Renderer.*`、`src/editor/observation/**` | B | M1-02 先补最小导航活动/结束状态，M3 再做观察；不得反向让 Renderer 依赖 editor |
| `src/editor/automation/**` | 当前通信所有者 | 不写 Scene/ViewModel；只调用冻结 API |
| `src/assets/SceneDocument.*`、`AssetManager.*`、`GltfImporter.*` | M3-02 的路径策略所有者，主代理明确交接 | 仅增加实际读取依赖前的授权钩子；A 不同时写这些文件；对应资产负面测试归该所有者 |
| `src/editor/MainWindow.*`、`main.cpp` | 主代理 | 仅装配/生命周期/必要 busy 聚合；其他 agent 提交接线要求 |
| `mcp/src/**`、`mcp/tests/**` | 当前 TS 所有者 | 协议与 schema 冻结后推进，不另造业务逻辑 |
| 新测试文件 | 所属模块所有者 | tests/CMakeLists.txt 仍归主代理；不多人写同一测试文件 |
| `docs/**`、README、progress.md | 主代理 | 子 agent 交证据文本；主代理统一落文档和只追加日志 |

两个实施者优先采用独立工作树，基线一致；无法隔离时使用上述互不重叠范围。隔离不等于允许自行提交/推送，Git 写操作仍需用户授权。所有构建缓存、测试夹具、服务管道与输出目录按 agent/task 隔离；不得同时写同一个 CMake build tree。

主代理也不得编辑已交出的文件。需要调整公共头/接口时：提交影响说明→主代理暂停相关写入→转交唯一所有者→更新契约/样例→通知全部消费者→重新验证。禁止覆盖、reset、清理他人未提交内容。

## 4. 依赖图与建议波次

```text
M0 契约/授权/互通原型
  └─ M1 身份、版本、busy、对象、历史
       ├─ M2 Core 网格准备 → 显式网格 API
       ├─ M3 有界桥/账本/路径（契约冻结后）
       └─ M3 真实观察（版本钩子冻结后）
              三者集成 → M4 MCP 最小闭环
                         ├─ M5 现有能力覆盖
                         └─ M6 Core 批次准备 → API 批次
                                  → M7 性能与部署验收
```

| 波次 | A | B | 主代理/审查点 |
| --- | --- | --- | --- |
| W0 | Q：Luna/max 只读源码/契约证据 | Q：Luna/max 官方资料；获批原型改由 Sol/max 实施 | 统一术语、确认安全边界、冻结 Schema |
| W1 | M1-01 → M1-02 → M1-03，API目录仍归A | 先补 M1-02 所需的导航活动/结束钩子，不提前展开观察改造 | 主代理接线；B前置钩子完成后再验收busy，不将查询任务跨给B |
| W2 | M1-04/05 | M2-01 Core 新对象候选 | 对象创建可先用已约定 Core 原语；有依赖时等待，不造临时空壳 |
| W3 | M2-02/03 | M3-04/05 观察 | 两条链以冻结版本接口协作 |
| W4 | M3-01/02/03 通信 | M4-01 TS 仅 mock/契约映射 | 通信权限/账本就绪前不得真实发写命令 |
| W5 | 修复自身问题或结束 | 独立 R 审查/另一实现者联调 | 主代理运行真实 E2E，形成 M4 门禁 |
| W6 | M5 按模块串行 API | 对应 TS 工具/独立测试 | 逐个方法验收后才在 describe 开启 |
| W7 | M6 API/历史集成 | M6 Core 候选准备，完成接口后交接 | 不能同时改 Scene；R 聚焦失败原子性 |
| W8 | 性能定标 | 包/宿主兼容验证 | 主代理最终整合、文档、风险列表 |

表是建议顺序而非强制填满两个槽位。W2/W7 有前置接口依赖时允许一人工作；不能为了“并行”在消费者里造猜测实现。

## 7. 开发协作不等于多 AI 同时改一个模型

多 agent 编码的并行，与未来多个建模 AI 向同一 Mini3D 文档发命令，是两种不同并发。

首版建模调用采用一个协调者拥有写通道；其他 AI 可以读摘要/截图并提供部件建议，但不能并行凭同一 documentRevision 写不同部件。协调者串行提交并分发新版本。多个客户端确实发写入时，后到者收到冲突而非自动合并。

开发隔离用独立文件/工作树；建模隔离用明确 document handle、组件身份和 revision。不能把开发代理的文件锁规则误当成运行期场景锁，也不为首版加多用户协同编辑系统。

## 8. 集成、暂停与恢复

集成顺序为：契约/公共头→Core准备能力→共享业务→观察/Bridge→TS→真实E2E。每次整合检查差异、头文件依赖、API/schema兼容、重复历史、通知次数和构建入口，再运行受影响验证。

用户要求暂停时，主代理停止新分派，通知运行中的 agent 停止安全写入并汇报已改文件/未完成验证，不启动后台续跑。恢复时先读任务状态、Git差异、现有产物和代理状态，只接续未完成项，不重复已确认的全量测试。

失败命令先读取实际错误，最多一次简单修正重试；第二次换策略。用户目录和当前窗口受保护：不得按 git.exe/pwsh.exe 名字批量结束进程；后台辅助程序使用隐藏窗口，仅按本任务记录的 PID/句柄清理其自有进程，不能关闭用户当前窗口或现有 Mini3D 会话。

## 9. 完成判定与回退

每任务“已验收”同时满足：目标实现；无越界差异；最终状态最小验证通过；真实风险由未参与实现者审查；progress.md 追加 What was done/Testing/Notes（含文件清单与回退点）；需要的使用文档同步。

回退不采用全仓 reset，也不删除宽泛输出目录。每任务保存基线和定向差异；已提交改动需经授权后对该任务 commit 使用 revert，未提交改动只反向移除本任务补丁并保留后续用户修改；progress 仅追加撤回说明。关闭通信开关只是功能止损，不等于撤回共用业务代码。

最终区分三个结论：

- M4：最小建模闭环可用。
- M7：本方案完整首版的适用测试与部署范围已验收。
- 实际牛高达作品：另一个使用任务，须恢复建模授权、重新读取参考并通过真实视口交付；不因 API 完成自动宣称模型完成。
