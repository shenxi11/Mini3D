# Mini3D 通用 API 与 MCP 扩展调研交接

Mini3D 已有可运行的场景编辑器和有限多边形建模内核，下一步要把这些能力变成可查询、可参数化、可撤销的通用编辑 API，再通过独立 MCP 适配器让 AI 建模。重点是统一业务入口，而不是把鼠标点击、菜单动作或场景文件直接改写包装成工具。

本交接面向后续参与调研的 AI 和工程人员。日期为 2026-10-06，代码基线为 [`5993c5c3f3cb7dd54810d0cb43c33a0e4e3e91fe`](https://github.com/shenxi11/Mini3D/commit/5993c5c3f3cb7dd54810d0cb43c33a0e4e3e91fe)，仓库为 [shenxi11/Mini3D](https://github.com/shenxi11/Mini3D)。下文明确区分现有能力、建议设计和需要调研的选择；API、通信桥及 MCP 均尚未实施。

## 当前产品与验证状态

Mini3D 是 Windows x64 桌面三维编辑器，使用 C++20、Qt 6 Widgets、OpenGL 4.1 Core、GLM 和 CMake。glTF 解析使用 fastgltf，JSON 使用 nlohmann/json，日志使用 spdlog，测试使用 Catch2 和 Qt Test。不依赖 Blender、Qt3D、Qt Quick 3D 或完整游戏引擎。

已完成二期 R2 获授权范围的 P0/P1 功能、性能收尾，以及后续工作台、无限网格、视图导航改动。此处的完成指现有范围，不表示完整 Blender 能力，也不表示全新机器、真实 mixed-DPI/输入法、长时间人工耐久及正式发布门槛全部通过。

最新代码提交同时保留正常构建与测试构建的分离：普通构建只编译 `mini3d_editor` 及其依赖，四个测试程序通过 `mini3d_test_suite` 单独构建；`ctest` 运行测试但不替代编译。本体后续新增 API 不应重新让日常运行连带编译测试。

| 能力 | 当前状态与边界 |
| --- | --- |
| 场景和对象 | 稳定对象 ID、父子层级、局部 TRS、复制/删除、名称/显隐、单层集合、撤销重做 |
| 基础几何 | Empty、Cube、Sphere、Plane；GUI 仅原生 Cube 可首次转为可编辑网格 |
| 文件与资产 | 静态 glTF/GLB 导入；原生 `.m3dscene` 保存/读取；写格式 3、读 1/2/3；所选几何导出 OBJ |
| 网格编辑 | 单对象点/边/面选择、组件变换、连通面域挤出、单个共面凸面内插、规则四边形带单环切、组件删除、单环共面补面 |
| 倒角 | 单条流形外凸边、单段，端点及邻面有明确限制；不是多边多段通用倒角 |
| 修改器 | 单轴 Mirror；1–2 级全四边网格 Catmull–Clark；固定 Mirror → Subdivision 顺序 |
| 外观与观察 | 实例乘色和纹理/顶点色开关、方向光、场景相机、编辑视角导航、正交/透视、真实 OpenGL 视口 |
| 自动化 | 已有测试/性能工具和显式验收截图入口；没有对外通用编辑 API、生产通信服务或 MCP 适配器 |

现有乘色不是完整 PBR 材质系统；球体、平面和静态导入对象不能直接进入 Edit；多对象同时 Edit、任意修改器栈、通用布尔和骨骼动画不属于上述已完成范围。API 必须如实报告支持条件，不得以外部参数绕过这些约束。

### 验证证据

- 布局与导航交付记录：Release CTest 4/4 组、451 用例、44,341 断言；Qt DPR 1/1.5/2 各 32 个界面用例、1,763 断言。见 [布局与导航说明](v2-blender-reference-layout-20261005.md) 和 [正式报告](validation/v2/blender-layout-20261005/report.json)。这是此前交付证据，不是本轮重新运行的完整回归。
- 构建分离记录：默认应用构建后 88 个测试产物的路径、长度、修改时间不变；独立测试构建成功。本轮 2026-10-06 再次运行现有 Debug `mini3d_unit_tests`，CTest 1/1 通过；未重新编译或重跑完整 GPU/UI 回归。
- 性能收尾在指定本机规则网格夹具上覆盖 1 万/5 万/10 万源点，不能推广为所有拓扑、算子或硬件的性能保证。见 [性能范围](v2-performance.md)。
- 正式验收仍有边界，见 [二期验收](v2-acceptance.md)。仓库代码、旧候选包和每阶段测量二进制不是同一概念，应分别核对构建及哈希。

## 现有架构和可复用入口

| 模块 | 现有职责 | API 扩展中的位置 |
| --- | --- | --- |
| `src/core` | 纯 C++ Scene、ID、TRS、多边形拓扑、建模算法、验证/派生、序列化 | 保留算法与数据规则；不引入 Qt Widgets、MCP 或通信协议 |
| `src/assets` | CPU 资源、glTF 解码、原子场景文件 IO、资源路径重建 | 继续处理文件与导入，不让适配器直接拼写场景文件 |
| `src/editor/SceneViewModel` | 场景、资产、选择、组件事务、唯一 QUndoStack、文档状态及 UI 通知 | 首版 API 的业务适配基础；渐进补齐显式目标和结构化结果 |
| `src/editor/operations` | UI 上下文、模态预览、操作登记和可重开历史 | 复用规则与历史，不把 QAction 或快捷键当成 API 契约 |
| `src/renderer_gl` | 只读场景消费、实际相机和视口、GL 生命周期 | 提供受控观察与真实图像反馈，不直接修改领域模型 |
| `MainWindow` | 控件、菜单、文件对话框、未保存确认与接线 | 装配 API 服务；不把请求解析和建模算法继续塞入窗口 |

最重要的现有入口为 [SceneViewModel.h](../src/editor/SceneViewModel.h)。已提供 `createEntity`、`setTransform`、`setSurface`、集合/文件操作、`makeEditable`、`replaceEditableMesh`、Mirror/Subdivision、组件 begin/preview/finish 事务和撤销重做。

Core 的 [EditableMesh.h](../src/core/modeling/EditableMesh.h) 可表示具有稳定点、面及面角 ID 的多边形网格；[Scene.h](../src/core/Scene.h) 提供候选准备、校验、派生及几何快照安装。任意多边形数据仍需满足现有验证规则，不等于可以安装任意无效拓扑。

现有 [OperatorRegistry.h](../src/editor/operations/OperatorRegistry.h) 有稳定操作名及上下文校验，但执行主要适配无参数 QAction，并依赖区域、当前选择和模式。它可提供命名及能力登记参考，不能直接作为完整外部 API。

## 通用 API 的目标和范围

这里的通用是指同一套编辑能力可以被 GUI、MCP、测试及后续脚本调用，而不是首版就支持所有语言、远程服务器或完整 Blender 算子。

建议首版采用应用内 C++ 编辑服务作为权威入口，再增加可序列化的本机调用协议。MCP 是该协议的一个客户端，不能反向规定 Core 数据模型。未来增加其他客户端时，复用同一参数契约和错误语义，不再重写建模业务。

首版边界为 Windows、本机、单用户、连接一个明确的编辑器实例、场景写入串行执行。生产级远程访问、多用户协作、后台建模线程、插件 ABI、Python 内嵌解释器及通用脚本执行不是首版目标；需要真实需求后再单独评估。

## 建议的分层

```text
GUI 控件 ───────────────┐
                       ▼
                   编辑应用服务
                       │
MCP 客户端             ├─ Scene / Assets / 建模内核
    │                  ├─ 唯一历史和文档状态
独立 MCP 适配器         └─ UI 通知与视口观察服务
    │                      ▲
本机协议与通信桥 ───────────┘
```

编辑应用服务接收有类型的查询和命令，负责目标检查、候选准备、提交、历史和通知。通信桥只负责连接、消息边界、协议解析及调度；MCP 适配器只负责工具/资源契约、参数转换和结果呈现，不持有可变 Scene 或第二个撤销栈。

建议先在 `src/editor/api/` 增加小范围 facade，复用 SceneViewModel 的入口，并定向补齐缺口。不要为建立 API 一次性搬迁全部 UI 和历史代码。当 facade 与 GUI 确实出现规则重复时，再提取共享应用服务，最终让两者调用同一逻辑。

`src/editor/api/`、`src/editor/automation/` 及独立 `mcp/` 是候选落点，不是已存在模块。独立 application target 是否必要，应由依赖和复用证据决定，而非先搭空架构。

## 本体必须补齐的能力

### 显式目标和完整参数

外部调用应传入对象 ID、父对象、变换空间、操作参数和必要版本，不从鼠标、当前输入框、3D 游标或全局选区猜目标。例如创建对象一次接收名称、几何、TRS 和颜色，而不是创建后再连续修改十几个属性，期间留下中间状态和多条历史。

当前 `duplicateSelected`、`deleteSelected` 以及部分组件操作依赖活动选择；创建基础体依赖游标；Object/Edit 和预览状态也影响是否可执行。需要新增明确目标的业务入口或受控上下文适配，但不能静默退出用户编辑模式、取消其预览或接管当前选区。

API 工作流应声明哪些操作改变选择、模式或相机；通常只读查询不改变这些状态。GUI 有未确认编辑时，首版建议返回 `BUSY`，让调用者明确选择稍后重试或请求允许的状态转换。

### 任意合法网格创建

Core 目前能校验和准备自定义 EditableMesh，但 GUI 的公开转换入口只支持 Cube，`replaceEditableMesh` 要求对象已绑定可编辑网格。需要新增一个完整业务入口：

1. 接收顶点位置、有序面环和可选面角属性，校验数量与拓扑。
2. 在本体分配稳定元素身份，返回输入序号到点/面 ID 的映射。
3. 准备对象、网格及派生数据，成功后一次发布；失败不留下空对象。
4. 成功产生可撤销命令，树、Inspector、覆盖层和 GL 缓存同步更新。

输入数组下标可以用于一条创建请求内部引用，但不应成为后续编辑身份。源网格与修改器求值网格必须分开查询；编辑作用于源笼，返回的新元素不能混淆为显示层拆点或三角化对角线。

### 参数化网格算子

挤出、内插、倒角和环切应以明确对象、源组件 ID 及参数调用现有内核。一个工具调用在本体内完成校验、候选计算、确认及历史，不要求 AI 维持跨多条请求的鼠标式模态会话。

返回结果应含变更版本、结果组件及新建/删除身份，支持 AI 下一步选中挤出的顶盖或倒角面。现有单面、单边、四边网格等限制应进入能力描述和错误详情，不能放宽内核校验来迎合工具请求。

### 查询快照与版本检查

对象列表、层级、局部/世界 TRS、可见性、颜色、包围盒、模式、未保存状态、修改器和网格统计应可结构化查询。大网格先返回摘要，再按对象/组件范围查询；不默认把所有顶点和三角形塞进 AI 上下文。

需要发布文档身份及变更版本。现有对象、拓扑元素 ID 和网格 topology/geometry/evaluation revision 可以复用，但运行期文档代际目前主要服务 UI 上下文，不是外部公共契约。

新建、打开、重载或服务重启应让旧文档句柄失效。修改命令提交前检查所声明的前置版本；版本冲突返回错误并保持状态，不操作新文档里恰好相同的 ID。各查询响应应来自一致的快照，而不是在变化中拼接字段。

### 历史与有界批处理

本体继续只有一套 QUndoStack。API 单次成功修改应形成合理的逻辑历史；无变化不增加历史，保存不清空历史。撤销是整份文档共享的操作，不能假装只撤销 AI 自己的上一次修改；调用者应检查文档与历史状态。

现有单网格候选/安装机制不是多对象原子事务。Qt `beginMacro/endMacro` 只负责历史分组，不自动保证失败回滚。Core 的整场景替换入口也不能直接等同于保留文档和历史的批量追加。

首版建议仅提供有数量/数据规模限制的批量创建和变换，先准备整组候选，再以复合命令提交；需要明确失败后场景、选择、历史保存点和通知的恢复语义。文件 IO、打开新文档、截图等不同副作用不要混入所谓可原子回滚的建模批次。

### 观察和真实截图

提供轴向/透视视图、明确对象聚焦、着色方式及真实视口图像。视角变化必须按现有 CameraState 与文档状态规则同步，不能只改 Renderer 后让保存值仍保留旧视角。

截图须在有效 Qt/OpenGL 生命周期内取得，绑定已确认的文档/几何版本、实际像素尺寸和相机状态。命令成功与下一帧已显示应是不同状态；不能用固定睡眠或拿旧帧冒充最新结果。关闭窗口或 Context 不可用时返回明确错误。

## 建议的 API 契约

以下名称与示例仅用于调研，不是可调用接口。建议以版本化、结构化的契约描述业务；传输层可以使用 JSON-RPC 2.0，但它只是封装，不应成为 C++ 内核依赖。

### 通用字段

- 标识：EntityId、MeshId、VertexId、FaceId、CornerId 及 revision 均按十进制字符串传递，避免 JavaScript Number 损失 64 位精度；边是规范化顶点 ID 对，不是任意边数组索引。
- 坐标：保持右手 Y-up；默认长度为现有场景单位，不擅自称为米或毫米。各参数说明 local/world 空间及枢轴；创建请求显式给位置，不依赖游标。
- 旋转：契约明确四元数顺序，建议 `[x,y,z,w]` 作为完整 TRS 表达；若提供欧拉角便捷接口，必须固定单位及顺序，不能与底层 GLM 构造顺序混用。
- 结果：区分成功、无变化、失败和提交结果未知；给出结构化错误码、中文说明及可执行修正信息。
- 约束：有限数值、有效旋转/非零缩放、几何规模、操作条件、路径范围在本体验证，不能只依赖 MCP JSON Schema。
- 版本：API 协议版本与 `.m3dscene` 文件版本独立；能力发现报告实际支持的操作、参数范围和限制。

请求示意：

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "method": "object.create",
  "params": {
    "documentId": "doc-session-example",
    "expectedDocumentRevision": "12",
    "name": "胸部装甲",
    "primitive": "cube",
    "parentId": "0",
    "transform": {
      "space": "local",
      "position": [0.0, 6.0, 0.0],
      "rotationQuaternion": [0.0, 0.0, 0.0, 1.0],
      "scale": [2.4, 1.5, 1.0]
    },
    "surface": {
      "tint": [0.12, 0.15, 0.22],
      "useVertexColor": false,
      "useTexture": false
    }
  }
}
```

成功结果示意：

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "result": {
    "documentId": "doc-session-example",
    "documentRevision": "13",
    "changed": true,
    "createdEntityIds": ["42"],
    "undoable": true
  }
}
```

JSON-RPC 解析/方法/参数错误使用协议规定的错误类别，业务错误通过应用错误范围及 `error.data.code` 细分，例如 `STALE_DOCUMENT`、`REVISION_CONFLICT`、`BUSY`、`INVALID_TOPOLOGY`、`UNSUPPORTED_OPERATION`、`PATH_DENIED`。不要只把 UI 的 bool 返回值包装成无法诊断的“失败”。

请求 ID 仅是响应关联，不天然提供幂等性。断线可能发生在提交之后，非幂等创建/挤出不能盲目自动重试。需要调研有界去重键、可查询结果与进程重启后的边界；不得承诺跨进程 exactly-once。

### 操作族

| 操作族 | 候选能力 | 首版重点 |
| --- | --- | --- |
| 应用与会话 | 版本、能力、实例、当前文档与忙碌状态 | 只连接明确实例，不自动控制全部窗口 |
| 场景与文件 | 场景摘要、打开、新建、另存、导入、OBJ 导出 | 未保存与覆盖保护，明确文件副作用 |
| 对象 | 查询、创建、复制、命名、TRS、显隐、换父、删除、集合归属 | 显式 ID 和完整参数，复用历史 |
| 网格 | 创建、摘要/拓扑查询、组件变换及现有建模算子 | 稳定源身份、版本条件、结果选区 |
| 修改器 | 查询、设置、启停、移除、应用 | 现有 Mirror/Subdivision 范围，不伪造任意栈 |
| 外观与光照 | 实例乘色、现有纹理/顶点色开关、场景相机/方向光 | 如实描述现有外观，不宣称完整材质编辑 |
| 历史与批次 | 状态、undo/redo、有界对象创建/变换批次 | 共享历史，批次失败语义可验证 |
| 视口观察 | 相机、聚焦、投影、着色、截图 | 真帧反馈，版本和图像相对应 |

本体登记可复用参数 Schema、操作限制及结果说明，C++ 强类型入口是实际执行权威；GUI 和 MCP 的契约检查应避免各维护一份不断漂移的参数表。是否由公共描述生成 MCP 工具，需要在原型中比较维护成本，不要求首版自动生成所有界面。

## 通信桥与 MCP 的候选方案

建议本机首版比较 Windows 命名管道与 loopback HTTP 两种方案，优先评估 Qt `QLocalServer/QLocalSocket`。命名管道减少端口及公网暴露问题，但需要核实 Node 客户端互通、当前用户访问权限、消息分帧、实例寻址与陈旧实例处理；它本身不等于完整访问控制。

使用 Qt 本地 socket 仍需 Qt Network 模块，当前顶层构建尚未声明该组件。只有采用该方案后才增加依赖和打包检查；本轮没有增加依赖或监听服务。远程/HTTP 身份验证、并发线程和权限边界变更均须单独确认。

生产服务默认关闭，由明确启动参数或应用入口开启；读写能力与可访问目录明确受控。首版所有模型写入在现有应用线程串行执行，不增加一条直接修改 Scene 的后台路径。连接不可用、请求超时、窗口关闭及用户编辑冲突应有清晰结果。

MCP 适配器建议采用独立 Node.js/TypeScript 程序和官方 SDK，客户端侧优先 stdio。SDK 当前支持的协议版本、Schema 工具链及宿主兼容性由后续调研核实后锁定，不凭历史示例固定版本。stdio 的 stdout 只输出协议消息，日志使用 stderr。

工具以少量明确语义组织，例如对象创建、网格操作、视口观察和保存；不要提供不受限的 `execute_code`、shell 或 UI 任意点击工具。大型查询使用结构化摘要/资源，截图使用 MCP 图像结果或宿主实际支持的资源形式，避免巨大 base64 文本挤满上下文。

MCP 不负责理解牛高达说明书或自动生成所有步骤；参考理解和建模策略属于调用方。MCP 只提供可组合能力及真实反馈，同一套 API 也应能制作普通机械件或建筑模型，而不是写死牛高达零件。

## 需要其他 AI 调研的具体问题

1. 对照现有 SceneViewModel 和历史实现，给出最小 facade 与共享应用服务的边界，哪些入口必须补显式对象参数，哪些可以直接复用；避免大规模重构。
2. 为自定义网格创建设计完整数据契约、身份分配/结果映射和原子创建过程，说明现有面角属性、默认材质与验证限制。
3. 为有界对象批次给出真正的候选准备、提交、失败恢复及历史方案，证明不是简单 Undo macro；明确不纳入事务的文件和渲染副作用。
4. 比较 Qt 命名管道与 loopback HTTP 的 Windows/Node 互通、依赖、访问控制和部署成本，给出推荐及最小互通原型方案，不扩展到公网服务。
5. 设计文档身份、revision、忙碌冲突、断线后结果确认和幂等边界，覆盖 GUI 与 AI 交替修改，而不是仅考虑 AI 独占软件。
6. 设计可查询的源拓扑、空间/法线/包围盒筛选和算子结果选择，减少工具调用数量；不要靠猜面数组顺序或屏幕像素选面。
7. 设计当前帧捕获与状态绑定，比较图像工具结果、MCP resource 和本机文件交付在目标宿主上的真实支持。
8. 核对官方 MCP SDK 和协议资料，提出可维护的工具划分及 Schema 复用方式；引用来源和核实日期，区分协议保证与项目自定义语义。
9. 根据现有建模内核评估牛高达外形复刻的必要操作，区分 API 缺口与几何算法缺口。多段倒角、布尔、完整材质等若非最小闭环所必需，不混入第一轮。

调研交付应包含现状证据表、推荐架构、参数与错误 Schema 草案、模块级改动清单、风险与替代方案，以及按依赖排列的实施/验收步骤。先给建议，不直接改源码、升级依赖、开放服务、提交/推送或替用户扩展授权。

## 建议实施顺序和验收条件

| 阶段 | 范围 | 验收条件 |
| --- | --- | --- |
| API 最小闭环 | 版本/场景查询、显式参数创建、TRS/颜色、另存及撤销 | GUI 与 API 看到同一对象和历史；失败保持状态；保存后重开一致 |
| 网格与批次 | 合法自定义网格、定向组件操作、有限批量对象命令 | 稳定 ID/版本正确；无效拓扑、过期句柄和批次中途失败不留半成品 |
| 本机通信和观察 | 显式开启服务、连接实例、协议分帧、忙碌拒绝、真实截图 | 通过真实运行本体调用，不直接制造场景文件；截图对应已确认版本 |
| MCP 适配 | 工具/资源、Schema、部署入口与客户端互通 | 从 MCP 完成查询→创建→编辑→查看→保存→重开，并检查失败路径 |
| 实际建模 | 基于说明书分阶段搭建牛高达 | 交付原生场景、正背面和透视截图，说明比例估算及未实现细节 |

针对性验收至少覆盖大整数 ID、非有限参数、旧文档/旧组件版本、未保存保护、目标消失、用户模态操作冲突、失败后历史/保存点不变、Undo/Redo、服务关闭和断线结果。图像检查使用 Mini3D 真实帧，不以 AI 效果图或仅算法测试代替软件结果。
