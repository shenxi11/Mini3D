# API MCP 性能校准

2026-10-06 的本机 Release 校准表明：规范 JSON 摘要优化降低了 1k/10k 创建的正式 pipe 延时，但 10k 创建仍有约 198 ms 的已观察入队前同步工作；1600×1000 聚焦截图主要耗时在 PNG 编码。这里记录的是 Windows 编辑器 API 命名管道性能，不是 MCP SDK、stdio、宿主界面和模型推理的完整用户端延时，也不构成跨机器响应时限承诺。

## 范围与口径

本机为 AMD Ryzen 7 5800H、16 个逻辑处理器、RTX 3050 Laptop、OpenGL 4.1 NVIDIA 610.47、Windows 11 25H2（10.0.26200）。工具链为 Qt 6.8.3、Node v24.13.0、PowerShell 7.6.5、MSVC 19.40.33811.0；探针使用 Release /O2 /MD，并显式使用可见的自有 Windows 视口。

每项正式行为取 20 个样本，截图取 10 个样本；各有 3 次预热，不计入统计，不剔除异常值。median/p95 均为 nearest-rank，以下时间单位为 ms；时间展示按记录的十进制值四舍五入到三位，精简 JSON 保留原始精度。截图独立运行中的其他行为只有 n=1，属于夹具完整性检查，不作正式行为延时结论。

typed 计时只含域调用，结果 DTO 编码在计时之外；typed 截图例外，计时到真实 PNG 完成为止，不含 base64 与 wire 编码。正式 pipe 计时包含外部 Node 请求 JSON 编码、命名管道往返及响应 JSON 解码，使用原生产对象。阶段数据来自四份测试专用插桩源码副本；正式对象版为主证据，插桩及每秒资源采样有观测成本。不能把 pipe−typed 当作精确解析成本，也不能相加各阶段分位数。

1k/10k 使用合法 `mesh.create` 的 40×25、100×100 四边格。100k 使用既有 `EditablePerformanceProbe` 的 400×250 算法，经新模型的 `makeEditable`/`replaceEditableMesh` 安装后只读采样：100,000 顶点、99,351 面、397,404 面角、198,702 派生三角；这不代表 API 能创建 100k 网格，不放宽 10k 创建上限。对象分页采用新建自有 Core Scene 的空对象夹具，不代表生产 API 的批量创建吞吐。

## 创建新旧对照

这是旧快照与新鲜构建的优化快照的成对复测，各项 n=20；相同 10k 请求帧 median 为 745,785 B，响应帧为 459,412 B。

| 夹具 | 旧 typed median/p95 | 新 typed median/p95 | 旧正式 pipe median/p95 | 新正式 pipe median/p95 |
| --- | ---: | ---: | ---: | ---: |
| 1,000 顶点 | 2.920/3.852 | 2.578/3.140 | 60.752/68.699 | 33.041/35.124 |
| 10,000 顶点 | 36.667/41.202 | 35.706/42.916 | 635.139/699.419 | 357.527/469.731 |

正式 pipe median 在这组样本中分别降低约 45.6% 与 43.7%；不承诺其他机器或后续任务保持固定比例。域调用本身没有同等幅度变化，主要收益来自摘要路径。

## 主要热点与同步阶段

下表来自 10k 创建的插桩请求，各阶段 n=20。占比先以每条请求的阶段实际时间除以该请求总时间，再取 median；分母是对应的插桩往返，不是正式版或 typed 的另一组样本。

| 阶段 | 旧 median/p95 | 新 median/p95 | 同请求总时间占比 median |
| --- | ---: | ---: | ---: |
| UTF-8 与预算扫描及 Qt JSON 解析 | 16.178/19.860 | 16.240/16.901 | 2.58% → 4.59% |
| 写参数规范化 | 107.273/125.215 | 106.924/114.467 | 16.96% → 30.22% |
| 规范 JSON 构造与 SHA256 | 352.852/374.529 | 73.907/79.675 | 55.72% → 20.92% |
| typed 参数解码 | 27.647/28.905 | 27.364/30.818 | 4.41% → 7.74% |
| 域计算 | 33.698/41.986 | 36.818/53.058 | 5.35% → 10.68% |

`canonicalDigestMs` 包含规范 JSON 构造和 SHA256，不是 SHA256 单独耗时。优化后写参数规范化仍约 107 ms，已成为更大的剩余成本。其他 DTO、wire、账本与队列阶段见精简 JSON；实际排队等待不是同步计算成本。

入队前观察到的同步工作，按每条请求的 UTF-8/预算/JSON、写参数规范化、digest、账本接收四个互不重叠阶段求和，再取分位数：

| 夹具 | 旧 median/p95 | 新 median/p95 |
| --- | ---: | ---: |
| 1,000 顶点 | 44.463/47.140 | 19.247/23.256 |
| 10,000 顶点 | 475.932/521.302 | 197.645/208.923 |

该值不含未计时的信封与校验胶水，仅描述这些入队前阶段；不能等同一次请求的完整连续 GUI 阻塞时间，也不能拿总往返时间直接宣称 GUI 被完整阻塞同样久。

## 聚焦捕获

新捕获在计时前调用现有 `focusEntities`；pipe 通过正式 `viewport.focus`。只有自建测试探针增加现有 `viewport.control`，100k 不具备 `scene.write` 或 `file.write`，生产默认权限与协议不变。相机、覆盖层和实际捕获视图写入报告；聚焦例图可见完整四边平面轮廓、网格及坐标轴。material 填充外观不用于肉眼证明 100k 内部拓扑，数量由 API 页及摘要核验。

以下均为 n=10，原图与输出尺寸一致；960 档是 960×640，1600 档实际为 1600×1000，不是 1600×1600，也不是把 960 图放大。

| 夹具 | 实际尺寸 | typed median/p95 | 正式 pipe median/p95 | PNG |
| --- | --- | ---: | ---: | ---: |
| 1,000 顶点 | 960×640 | 43.948/46.000 | 64.400/79.609 | 290,228 B |
| 10,000 顶点 | 960×640 | 43.690/47.514 | 48.084/50.417 | 290,230 B |

## 旧持续窗口与资源

旧完整基线的 194,704 次持续调用来自 5 个场景 × 正式/插桩两组的 10 个独占探针进程汇总。每个进程只有 5 个各 5 秒的持续窗口，另有前后两个各 3 秒的空闲窗口；它不是单实例完成 194,704 次调用的耐久验证。1k/10k 页查询穿插同名 `entity.update` 的 `no_change`，不人为堆 Undo；100k 和对象档只查询。

记录到的队列最大值为 16，结果账本缓存最大为 10,594,117 B（限额 16 MiB），会话最大为 1；私有账本/会话计数只在插桩版可见。持续窗口的首尾 Undo 历史计数一致，最早写结果确认为 `result_expired`。正式 10k 最后一个窗口的 PrivateBytes 首尾均为 287,920,128 B，WorkingSet 均为 273,661,952 B；其余窗口可能有分配阶梯和波动，不能由短窗口推出无泄漏或无限驻留。

20 个空闲窗口的单核等效 CPU 记录范围为 0–0.78125%，其中 19 个为 0%；唤醒约 1.969–2.001 次/秒。探针本身有每秒一次的资源统计计时器，Windows 进程 CPU 时间也有计量粒度，不承诺真实后台成本为零。

优化后创建与聚焦截图运行的持续窗口数为 0；旧资源结论不冒充优化后长时间验证。

## 调用建议与复跑

交互调用优先取所需的 256 项源页，避免为了少量数据反复生成 100k 完整摘要；该摘要在本机约 300 ms。10k 创建仍是数百毫秒级请求，不适合高频重建；进一步优化应先针对已测到的参数规范化成本，不自动收紧生产限额或修改协议、线程与权限。

截图由客户端显式按用途选择 `longestEdge`，需要更高细节时再请求 1600；本机实测的高分辨率 PNG 编码是主要成本。960 是基础探针的选择，不表示生产默认或 API 上限已改。

先准备匹配的现成 Release 库、Qt、vcpkg、Node 和 PowerShell 7.6；路径及其他参数见 [性能工具 README](../tools/api-mcp/performance/README.md)。创建复测的示例：

```powershell
$performanceArgs = @(
    '-NoLogo', '-NoProfile', '-NonInteractive', '-File',
    'E:/Mini3D/tools/api-mcp/performance/run.ps1',
    '-Cases', 'mesh:1000,mesh:10000', '-Samples', '20', '-Warmup', '3',
    '-CaptureSamples', '10', '-WindowCount', '0'
)
& pwsh @performanceArgs
if ($LASTEXITCODE -ne 0) { throw 'Performance run failed.' }
```

聚焦捕获保持 `-Warmup 3 -CaptureSamples 10 -WindowCount 0`，分别改为 `-Cases 'mesh:100000' -Samples 1 -CaptureLongestEdge 960` 或 `-Cases 'mesh:1000' -Samples 1 -CaptureLongestEdge 1600`。可用首轮输出的已验证 `probeBuild` 作为 `-ExistingProbeBuild`，只在源码、库及工具仍匹配时复用。旧完整持续矩阵的配置为五场景、`-Samples 20 -Warmup 3 -CaptureSamples 10 -WindowSeconds 5 -WindowCount 5`；现在执行它得到的是当前工具和库的新结果，不会重建旧 cropped 基线。

复跑需独占性能窗口，暂停其他 GUI/构建重负载，使用 E/D 盘独占 scratch，保留全部新输出，不覆盖旧证据。工具只关闭自己拥有的进程。当前聚焦客户端不能直接与未授予 `viewport.control` 的旧裁切探针配用；旧 A/B 再测需要匹配的源码、库与工具快照。本轮没有在其他用户、机器或宿主上复测。
